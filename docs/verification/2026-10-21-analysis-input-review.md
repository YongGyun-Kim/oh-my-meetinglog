# 파일 재생 실패와 분석 입력 구조 리뷰

확인일: 2026-10-21. 사용자가 제공한 약 28분짜리 M4A 파일을 로컬에서 확인했다. 이 문서에는 대화 본문을 기록하지 않는다. 실행 자료와 분석 결과는 Git에서 제외된 `data/verification-2026-10-21/`에 둔다.

후속 변경: 2026-10-22부터 전사는 턴 안의 문장 목록으로 저장하며, 정리 입력·출력에서 음성 시간을 제거했다. 아래는 2026-10-21 당시의 구현과 검증 기록이다. 시간 범위를 서버에서 계산하자는 당시 제안은 채택하지 않았다. 현재 구조는 [README](../../README.md#단계별-데이터)를 따른다.

## 확인한 오류

### P1. M4A 컨테이너만 확인하고 코덱 호환성을 확인하지 않았다

- 원본: ALAC, 48kHz, 모노, 1,690.624초, 154,469,566바이트.
- 기존 API는 M4A를 `audio/mp4`로 보내며, 내부 코덱을 확인하지 않았다.
- Chromium에서 `audio/mp4; codecs="alac"`의 지원 응답은 빈 문자열이었다. 실제 파일도 `MEDIA_ERR_SRC_NOT_SUPPORTED`와 `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`로 실패했다.
- FFmpeg는 읽을 수 있어 전사가 진행됐다. 전사 가능 여부와 브라우저 재생 가능 여부가 달랐다.

컨테이너와 브라우저별 코덱 지원은 [MDN 코덱 안내](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs)에서도 구분한다.

수정: MP4 안의 코덱이 AAC·MP3가 아니면 재생용 PCM WAV를 별도로 만든다. 원본의 표본화율과 채널 수를 유지하며, 원본 파일은 변경하지 않는다. 재생용 파일은 16비트 PCM이고 원본과 비트 단위로 같은 음성 파일이라는 뜻은 아니다. WebM은 기존처럼 재인코딩 없이 길이 정보만 보완한다. 두 경로 모두 임시 파일에서 변환한 뒤 교체하고 재사용한다.

### P1. 분석 구간을 잘못 계산해 호출이 증가했다

| 항목                                     | 수정 전 확인값 |
| ---------------------------------------- | -------------: |
| 저장용 전사 JSON                         |  297,245바이트 |
| 발언                                     |          476개 |
| 단어별 정렬 정보                         |        2,865개 |
| 유효 본문                                |   23,724바이트 |
| 전체 전사를 한 번 요청으로 구성한 메시지 |  101,243바이트 |
| 실제 계획된 분석 구간                    |           20개 |

실제 모델 입력에는 단어별 시각이나 수정 전 원문을 보내지 않는다. 하지만 분할 코드는 이 정보를 포함한 저장용 `Transcript` 전체를 기준으로 크기를 계산했다. 그 결과 실제 요청은 약 6~8KB인데도 16KB 한도에 도달한 것으로 처리했다.

수정: 시스템 안내와 실제 전송 메시지의 UTF-8 크기로 분할한다. 단어 정보가 많다는 이유만으로 분석 호출이 증가하지 않도록 검사한다.

### P1. 정상적으로 구간을 처리해도 전체 시간 제한에 걸렸다

- 음성 처리는 약 90초 만에 완료됐다.
- 분석 전체 제한은 음성 길이의 25%인 약 422.7초였다.
- Ollama 로그에서 처음 네 요청은 각각 약 80초·95초·76초·68초 만에 완료됐다. 다섯 번째 요청 도중 워커가 전체 제한 시간에 도달했다.
- 저장된 오류는 `stage_timeout`, 실패 단계는 `analysis`다.

수정: 분석은 구간 또는 전체 요약 요청이 완료됐다는 진행 이벤트를 받으면 대기 시간을 다시 계산한다. 진행이 없는 엔진은 기존처럼 중단하며, 취소·프로세스 종료와 HTTP 요청 제한도 유지한다. 단순히 모든 작업의 최대 시간을 늘리지는 않는다.

### P2. 모델에 영구 ID를 반복 전달하고 있었다

발언 ID 476개와 화자 ID 대부분이 36자 UUID다. 입력뿐 아니라 모델의 근거 인용에도 긴 ID가 반복된다.

수정: 한 번의 분석 안에서 `t1`, `t2`, `s1`, `s2`로 바꾼다. 결과의 근거 ID와 담당자 ID는 원래 UUID로 되돌려 검증한 뒤 저장한다. 저장·내보내기 계약은 유지한다.

### P2. 구간마다 모델을 해제하고 다시 로드했다

기존 요청은 `keep_alive: 0`을 사용했고, 요청 종료 시 추가 해제 요청도 보냈다.

`keep_alive: 0`은 즉시 해제를 요청하는 값이다. [Ollama API 문서](https://docs.ollama.com/api/chat)

수정: 연속 분석 동안에는 모델을 유지한다. 전체 분석이 성공하거나 실패하면 연결을 닫고 모델 해제를 요청한다. 워커 취소·시간 초과의 해제 경로도 유지한다. 이 비용을 줄였다는 사실과 총 처리 시간이 얼마나 줄었는지는 구분한다.

### P2. 기한 검증 재시도에 잘못된 항목을 알려 주지 않았다

실제 재분석에서 두 번 생성한 기한이 모두 근거 검증에 실패했다. 기존 재시도는 `unspoken_due_date`라는 코드만 전달했다. 어느 기한과 근거 ID를 수정해야 하는지 전달하지 않았다.

수정: 재시도 입력에 문제가 된 기한 값과 근거 발언 ID를 JSON으로 전달한다. 원문 표현을 사용하거나 미정으로 남기도록 안내한다. 근거 검증과 재시도 횟수는 유지하며, 잘못된 결과를 통과시키지 않는다.

## 모델에 전달하는 데이터

아래는 구조를 보여 주기 위한 가상 예제이며 실제 대화가 아니다.

```json
{
  "speakers": [{ "id": "s1", "display_name": "화자 A", "role": null }],
  "turns": [
    {
      "id": "t1",
      "speaker_id": "s1",
      "start_ms": 1000,
      "end_ms": 3000,
      "text": "18일에 초안을 공유하겠습니다."
    }
  ]
}
```

| 정보                                              | 판단                                                                                                                             |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 수정문 우선 본문                                  | 필요. 자동 전사 원문과 수정문을 동시에 보내지 않는다.                                                                            |
| 짧은 발언 ID                                      | 필요. 결과의 근거를 원문으로 연결한다.                                                                                           |
| 짧은 화자 ID와 화자 정의                          | 필요. 누가 제안·약속했는지 구분하며, 실제 이름이나 역할을 추측하지 않는다.                                                       |
| 발언 시작·끝 시각                                 | 현재는 주제 시간 범위 생성과 검증에 사용한다. 제거하려면 모델 출력의 시간 정보를 근거 ID에서 서버가 계산하도록 함께 바꿔야 한다. |
| 단어별 정렬, 원문 이력, 작업·모델 이력, 파일 경로 | 모델에 보내지 않는다. 저장·내보내기 정보와 분석 입력을 구분한다.                                                                 |
| 검토 표시                                         | 현재 모델 입력에는 없다. 불확실한 구간을 판단에 반영할지는 후속 검토가 필요하다.                                                 |

JSON의 키 이름을 반복하는 비용은 남아 있다. 배열과 열 정의로 바꾸면 더 줄일 수 있지만, 모델이 열 순서를 잘못 읽는지까지 비교해야 한다. 이번에는 영구 ID 단축, 공백 제거, 실제 요청 크기 기준 분할을 먼저 적용했다.

출력에서도 주제별 논의·질문과 답변·전체 요약이 일부 중복될 수 있다. 이 구조를 줄이는 일은 UI와 내보내기에도 영향을 준다. 실제 결과에서 어떤 항목을 사용하지 않는지 확인한 뒤 별도로 변경한다.

## 검증

- 회귀 테스트에서 ALAC 입력의 WAV 재생 응답, 표본화율·채널 수, 원본 보존, 캐시 재사용, 부분 요청을 확인한다.
- 단어별 시각이 분할 경계를 바꾸지 않는지 확인한다.
- 짧은 근거·담당자 ID를 원래 ID로 되돌리는지 확인한다.
- 분석 진행 이벤트가 있으면 계속 처리하고, 진행이 없는 프로세스의 중단·취소가 유지되는지 확인한다.
- 실제 전사로 계산한 분할은 20개에서 5개로 줄었다. 구간 요청 메시지 합계는 139,935바이트에서 75,698바이트로 약 45.9% 줄었다. 전체 요약 요청과 재시도는 별도다. 응답 스키마와 HTTP 바깥의 필드 크기도 이 수치에 포함하지 않는다.
- 실제 파일의 수정된 재생 API를 Chromium에서 확인했다. 오류 없이 재생이 진행됐고 끝부분 탐색 후에도 전체 길이는 고정됐다. 디코딩된 길이는 약 1,690.539초로 컨테이너 표기보다 약 0.085초 짧다.

### 실제 재분석과 앱 복구

- 환경: Apple M5 Pro, 메모리 48GB, Ollama 0.31.1, `gpt-oss:20b`.
- 저장된 476개 발언의 전사를 `AnalysisService`에서 재사용했다. 음성 전사를 다시 실행하지 않았다.
- 최종 재분석은 666.120초에 완료됐다. 모델 요청은 8회다. 구간 분석 5회, 기한 근거 재시도 1회, 전체 요약 1회, 전체 요약의 형식 재시도 1회다.
- 전체 요약 첫 요청은 생성 토큰 4,096개 한도에서 중단됐고 본문은 비어 있었다. 추론만 생성한 상태였으며, 기존 형식 재시도에서 정상 결과를 받았다. 요약 단계의 추론량과 출력 한도는 추가 성능 검토 대상이다.
- 결과는 주제 26개와 할 일 15개다. 영구 ID 복원 후 근거 ID·화자 ID·기한 원문·주제 시간 범위 검증을 통과했다.
- 완료한 검증 결과를 `recovered_result` 이력이 있는 새 분석 작업으로 저장했다. 원래의 `stage_timeout` 실패 이력과 전사 버전은 유지했다. 복구 작업의 시간과 모델 재분석 시간은 구분한다.
- 개발용 웹·API·워커를 재시작한 뒤 실제 기록 화면에서 대화 개요 표시, `succeeded` 상태, `analysis_stale: false`, 음성 재생과 WAV 부분 응답(206)을 확인했다. 별도의 검증용 API는 종료했다.
- 로컬 원본과 업로드한 원본의 SHA-256이 같았다. 분석 종료 후 `ollama ps`에서 로드된 모델이 없는 것을 확인했다.
- 전체 검사: Python 81개, 웹 컴포넌트 16개, 브라우저 3개 통과. 정적 검사·타입 검사·빌드도 통과했다.

기존 실행은 시간 초과로 끝났으므로, 완주 시간의 전후 속도 개선율은 계산하지 않는다. 근거 ID·형식 검증 통과만으로 요약의 의미적 정확성이 보장되지는 않는다.
