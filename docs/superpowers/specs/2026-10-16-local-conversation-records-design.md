# 한국어 대화 기록 서비스: 로컬 웹 MVP 설계안

작성일: 2026-10-16

상태: 사용자 검토용 설계안. 제품 코드는 아직 구현하지 않았다.

## 1. 목적과 확정된 조건

마이크 녹음 또는 기존 녹음 파일을 받아, 누가 언제 무엇을 말했고 어떤 주제로 어떻게 논의했는지 확인할 수 있는 대화 기록을 만든다. 사람이 읽는 기록과 다른 AI가 재사용할 수 있는 구조화 데이터를 함께 제공한다.

사용자와 확인한 조건:

- 첫 사용 사례는 **한국어 1:1 인터뷰·상담**이다.
- 첫 버전은 개인 PC의 로컬 웹에서 실행하고, 나중에 서비스로 확장한다.
- 마이크 녹음과 기존 음성 파일 입력을 모두 지원한다.
- 실시간 자막은 필요하지 않다. **녹음 종료 후 정확한 결과**를 제공한다.
- 품질과 속도가 충분한 처리는 PC에서 끝낸다. 부족한 단계에는 외부 API를 사용할 수 있다.
- Plaud의 음성 입력, 전사, 화자 구분, 대화 정리 흐름을 참고한다.

이 문서에서 제안하는 초기 기본값:

- macOS Apple Silicon과 Chrome을 우선 지원한다.
- 한 파일은 최대 2시간·1GB로 제한한다. 녹음도 최대 2시간으로 제한하고 종료 전에 안내한다.
- 로그인 없이 한 사람이 사용하며, 원본과 기록은 로컬 디스크에 저장한다.
- 화자는 먼저 A/B 등으로 표시하고, 사용자가 이름과 역할을 지정한다.
- 인터뷰와 상담에 공통인 기록 양식을 먼저 제공한다. 상담의 전문 분야는 아직 정해지지 않았다.

## 2. 처리 방식 비교와 추천

| 방식 | 장점 | 제약 | 판단 |
| --- | --- | --- | --- |
| 로컬 우선, 부족한 단계에 API | 로컬 성능을 활용하면서 품질 부족을 보완할 수 있다 | 단계별 검증과 처리 이력 관리가 필요하다 | 사용자 조건에 맞는 추천 방식 |
| 모든 처리 로컬 | 모델 준비 후 인터넷 없이 처리할 수 있다 | 하드웨어·모델 성능의 한계를 그대로 받는다 | 선택 가능한 실행 모드로 제공 |
| API 우선 | 로컬 모델 준비가 적다 | 네트워크와 API 비용에 의존한다 | 비교 및 재처리용 모드로 제공 |

‘로컬 우선’은 매 녹음의 정확도를 AI가 완벽하게 판정한다는 뜻이 아니다. 대표 한국어 녹음으로 엔진을 비교하고, 검증을 통과한 로컬 엔진을 단계별 기본값으로 선택한다. 실행 중에는 명확한 실패, 결과 형식 오류, 처리 시간 초과를 기준으로 대체 경로를 사용한다. 음성 품질이 나쁘거나 화자가 불확실하면 검토할 부분을 표시한다.

## 3. 첫 버전의 사용자 흐름

1. 기록 목록에서 **새 녹음** 또는 **파일 가져오기**를 선택한다.
2. 마이크 권한과 입력 레벨을 확인하고 녹음한다. 파일 입력은 MP3, M4A, WAV, WebM을 지원한다.
3. 녹음을 종료하거나 파일 업로드가 끝나면 처리 작업을 등록한다. 화면에는 현재 단계와 경과 시간을 표시한다.
4. 전사와 화자 구분이 끝나면 분석 완료 전에도 대화 원문을 확인할 수 있다.
5. 화자 A/B에 이름과 역할을 지정하고, 발언을 눌러 원본의 해당 시점을 재생한다. 잘못 인식한 텍스트와 화자 배정을 수정한다.
6. AI 기록에서 전체 요약, 주제별 논의 흐름, 질문과 답변, 명시된 합의, 미해결 질문, 후속 할 일을 확인한다.
7. 원문을 수정한 경우 기존 분석에 ‘이전 전사 기준’ 표시가 나타난다. **다시 분석**으로 최신 기록을 만든다.
8. Markdown과 JSON으로 내보낸다. 재실행 후에도 기존 기록을 조회할 수 있다.

화면은 기록 목록, 녹음·가져오기, 기록 상세, 설정의 네 가지로 구성한다. 상세 화면의 핵심은 음성 플레이어, 화자별 전사, 분석 결과다. 넓은 화면에서는 전사와 분석을 나란히 보여주고 좁은 화면에서는 탭으로 전환한다. 엔진 이름은 기본 대화 화면 대신 설정과 처리 상세에 표시한다.

## 4. 결과의 정확성을 지키는 규칙

- 원본 음성, 엔진이 생성한 전사, 사용자가 수정한 전사를 구분해 보관한다.
- AI 요약이 전사 원문을 덮어쓰지 않는다. 발언의 부정 표현, 수치, 조건을 임의로 정리해서 바꾸지 않는다.
- 주제별 요약과 질문·응답에는 근거 발언 ID를 연결한다. 클릭하면 해당 발언과 음성으로 이동한다.
- 실제 이름, 인터뷰어·응답자 역할, 담당자, 기한은 발언이나 사용자 입력에 없으면 추정해서 채우지 않는다.
- 결정이나 후속 할 일이 없는 대화에서는 해당 목록을 비워 둔다.
- 발언이 잘 들리지 않거나 화자가 불확실한 구간을 표시하고 사용자가 확인할 수 있게 한다. 엔진에 없는 신뢰도 값을 만들어내지 않는다.
- 겹쳐 말한 구간은 겹침 정보를 보관한다. 화자 구분은 발언을 사람별로 배정하는 기능이며, 각각의 깨끗한 음성 트랙을 만드는 기능은 첫 범위에 포함하지 않는다.
- 분석은 대화에서 확인한 내용을 기록한다. 음성만으로 성격이나 심리 상태를 단정하는 항목은 생성하지 않는다.

## 5. 시스템 구조

React·TypeScript·Vite 웹 화면과 Python·FastAPI 서버를 사용한다. Python은 음성 모델 실행과 전처리를 맡고, React는 녹음·재생·편집을 맡는다. 서버는 기본적으로 `127.0.0.1`에서만 수신한다.

별도 워커 프로세스 하나가 SQLite에 저장된 작업을 순서대로 처리한다. 모델 추론은 HTTP 요청 안에서 실행하지 않는다. 첫 버전에는 Redis나 분산 작업 서버를 추가하지 않는다.

| 구성 요소 | 책임 | 입력과 출력 |
| --- | --- | --- |
| 웹 화면 | 녹음, 업로드, 재생, 전사 편집, 기록 확인 | 서버 API의 기록·작업·분석 데이터 |
| API 서버 | 파일 검증, 기록 관리, 편집 버전 관리, 작업 등록 | HTTP 요청 → SQLite·파일 저장소 |
| 작업 워커 | 단계 실행, 체크포인트, 재시도, 취소 | 작업 ID → 단계별 결과물 |
| 음성 처리기 | 디코딩, 음성 구간 탐지, 전사, 시간 정렬, 화자 구분 | 음성 파일 → 화자·시간이 있는 발언 |
| 분석 처리기 | 대화 구조화, 근거 연결, 결과 검증 | 전사 버전 → 분석 버전 |
| 저장소 | 원본과 결과물 보존 | SQLite 메타데이터 + 로컬 파일 |

외부 엔진 결과도 동일한 발언·분석 데이터 형태로 변환한다. 향후 서버로 옮길 때 웹 API와 데이터 형식은 유지하고, 파일 저장소·작업 실행·DB를 교체할 수 있도록 경계를 둔다. 첫 버전에서 배포 플랫폼이나 멀티테넌트 구조를 만들지는 않는다.

## 6. 음성 처리 단계

`입력 저장 → 디코딩·검증 → 음성 구간 탐지 → 전사·화자 구분 → 시간·화자 결합 → 대화 분석 → 내보내기`

### 입력 저장과 전처리

원본은 보존하고 FFmpeg로 모델용 음성을 별도 생성한다. 음성 구간 탐지로 무음과 비음성 구간을 식별하되, 원본 시간축은 유지한다. 불필요한 음성이 전사되는지 검사하며, 음성이 없는 파일은 ‘인식된 음성 없음’으로 종료하고 AI 분석을 실행하지 않는다.

긴 입력은 모델의 길이 제한에 맞게 나누되, 원본 기준 오프셋과 경계의 중복 구간을 기록한다. 중복 발언을 제거하고 단어가 잘리지 않게 결합한다. 음량 보정은 별도 처리 파일에 적용하고, 강한 잡음 제거를 무조건 적용하지 않는다.

마이크 녹음은 MediaRecorder의 데이터를 주기적으로 서버에 저장한다. 순번과 수신 상태를 기록하고 정상 종료 후 하나의 유효한 컨테이너로 결합·검증한다. 탭 종료 시 이미 수신한 데이터를 보존하되, 비정상 종료된 컨테이너의 완전한 복구를 보장하지는 않는다. 녹음 중 저장 실패를 사용자에게 알린다.

### 로컬 엔진 후보

| 단계 | 첫 검증 후보 | 선택 근거와 검증 사항 |
| --- | --- | --- |
| 전사 | MLX-Audio의 Qwen3-ASR-1.7B, Qwen3-ForcedAligner | 한국어를 지원하고 Apple Silicon 실행 경로가 있다. 실제 대화 정확도와 시간 정렬을 검증한다 |
| 전사 비교 기준 | MLX Whisper large-v3 | 같은 녹음에서 정확도와 처리 시간을 비교한다. 제품에 두 모델을 항상 동시에 실행하지 않는다 |
| 화자 구분 | MLX-Audio의 Sortformer v2.1 | Apple Silicon 실행 경로를 사용하고, 긴 녹음에서도 화자 ID가 유지되는지 검증한다 |
| 대화 분석 | Ollama의 설치된 `gpt-oss:20b` | 기존 로컬 모델로 한국어 기록 품질과 구조화 출력을 먼저 검증한다 |

검증 전에는 어떤 후보도 한국어 1:1 대화에서 가장 정확하다고 확정하지 않는다. 화자 구분 후보가 기준을 충족하지 못하면 pyannote Community-1을 비교한다. 이 모델은 다운로드 조건 수락과 Hugging Face 토큰이 필요한 초기 준비를 안내하고, 준비 후 로컬 실행을 지원한다.

화자 구분은 녹음 전체에서 일관된 화자 ID를 유지한다. 잘라낸 음성마다 나온 A/B 번호를 그대로 이어 붙이지 않는다. 전사의 단어·구간 시각과 화자 구간을 결합하고, 배정할 수 없는 발언에는 미확인 표시를 남긴다. 초기 예상 인원은 두 명이며, 입력에 다른 음성이 있을 때 억지로 둘 중 한 사람으로 확정하지 않는다.

### 외부 API 경로

첫 외부 후보는 OpenAI다. 음성은 `gpt-4o-transcribe-diarize`의 `diarized_json`, 분석은 Responses API의 `gpt-5-mini`와 JSON Schema를 사용한다. 모델명은 서버 설정으로 교체할 수 있다. 실제 계정에서의 사용 가능 여부는 초기 연결 검사로 확인한다.

이 음성 API는 전사와 화자 구분을 함께 제공하므로, 이 경로를 택하면 두 단계를 하나의 새 결과 버전으로 생성한다. 로컬 결과의 텍스트와 외부 결과의 화자 번호를 검증 없이 섞지 않는다. 음성 처리 결과가 충분하면 분석만 외부로 보낼 수 있으며, 이때 음성 대신 전사만 전송한다.

외부 음성 요청은 25MB 제한 안에 맞춰 압축하고, 30초를 초과하면 `chunking_strategy="auto"`를 사용한다. 최대 입력 길이에서는 먼저 단일 요청에 들어가는 비트레이트로 인코딩하고, 실제 파일 크기를 검사한다. 여전히 나눠야 한다면 겹침 구간과 짧은 화자 참조 음성으로 청크 간 화자를 연결한다. 대응이 불확실하면 미확인 상태로 남기고 수정할 수 있게 한다.

### 실행 모드와 전환

- **자동**: 검증된 단계별 로컬 기본값을 사용한다. 모델 미준비·지원 불가·실행 실패·단계 시간 제한 초과·출력 검증 실패에는 설정된 API 경로를 사용한다. 모델을 아직 검증하지 않은 경우 그 상태를 표시하며, 결과 정확도를 보장한 것으로 취급하지 않는다.
- **로컬만**: 외부 요청 없이 처리한다. 사용할 수 없는 단계는 원인과 해결 방법을 표시한다.
- **API 사용**: 설정된 외부 경로로 새 결과를 만들거나 다시 처리한다.

API 키가 없으면 로컬 경로는 사용할 수 있고 외부 전환은 실행하지 않는다. 외부 사용이 이미 설정된 작업마다 다시 허가를 요구하지 않는다. 처리 결과에는 실제 실행 장소와 모델, 전환 이유를 남긴다. API 키는 서버 측 비밀 설정에 두고 브라우저 응답·로그·내보내기에 포함하지 않는다.

모델 다운로드·연결 설정은 녹음 처리와 구분한 사전 준비 작업이다. 로컬 전용 처리 중에는 모델을 자동 다운로드하지 않고, 로컬 LLM 연결도 루프백 주소의 설치된 모델로 제한한다.

기본 시간 제한은 각 음성 단계에 `max(180초, 음성 길이 × 0.5)`, 분석 단계에 `max(300초, 음성 길이 × 0.25)`로 설정한다. 제한은 구성 가능하며, 이는 오류 복구 기준이다. 아래의 성능 목표와 구분한다. 모델 다운로드는 별도의 준비 작업으로 취급한다.

## 7. AI가 재사용할 수 있는 기록 형식

JSON을 원본 데이터 형식으로 삼고 화면과 Markdown은 같은 데이터로 만든다. 내보내기에는 `schema_version`, 기록 ID, 전사 버전, 분석 버전, 언어, 길이, 생성 시각, 처리 이력을 포함한다. 시간은 원본 음성 시작을 기준으로 한 밀리초 정수다.

| 데이터 | 필수 정보 |
| --- | --- |
| 기록 | ID, 제목, 입력 종류, 생성 시각, 길이, 처리 상태 |
| 화자 | 기록 내 ID, 표시 이름, 사용자가 지정한 역할 |
| 발언 | 안정적인 ID, 시작·종료 시각, 화자 ID 또는 미확인, 원문, 수정된 텍스트, 검토 표시 |
| 전사 버전 | 버전 ID, 발언 목록, 원본 엔진 결과 참조, 생성 원인 |
| 분석 버전 | 기준 전사 버전, 생성 모델·프롬프트 버전, 검증 결과 |

분석 결과의 공통 구조:

- `overview`: 대화 종류, 전체 요약, 주요 주제. 전체 요약에도 근거 발언 ID를 연결한다.
- `topics[]`: 주제명, 시작·종료 시각, 논의 순서, 서로 다른 의견, 정리된 내용, 근거 발언 ID.
- `question_answers[]`: 질문과 질문 발언 ID, 답변 요약과 답변 발언 ID. 답변이 없으면 답변은 null이다.
- `agreements[]`: 발언에서 확인되는 합의·결정과 근거 발언 ID.
- `open_questions[]`: 대화 안에 남아 있는 질문과 근거 발언 ID.
- `actions[]`: 할 일, 명시된 담당 화자 ID 또는 null, 명시된 기한 또는 null, 근거 발언 ID.

분석에는 해당 요청에 제공한 발언 ID만 인용하도록 지시한다. JSON 형식과 ID 존재 여부는 프로그램으로 검사하고, 근거가 실제 내용을 뒷받침하는지는 별도 품질 검증으로 확인한다. 형식 일치가 사실 정확성을 보장한다고 취급하지 않는다.

긴 전사는 발언 경계에서 나눠 질문·응답 문맥이 이어지도록 인접 발언을 겹쳐 제공한다. 구간별 결과를 합칠 때 원래 발언 ID를 유지하고 중복을 제거한다. 마지막에 전체 흐름과 주제 간 연결을 정리한다. 전사를 무조건 잘라서 입력 한도를 맞추지 않는다.

## 8. 저장, 편집, 재처리

기본 데이터 디렉터리는 프로젝트의 `data/`이며 환경 설정으로 바꿀 수 있다. SQLite와 원본·처리 파일을 저장하고 Git에서 제외한다. 기록 ID로 파일 경로를 생성하며 사용자가 보낸 파일명을 저장 경로로 사용하지 않는다.

- 엔진 결과와 분석 결과는 버전별로 보존한다. 전사 재생성 결과는 새 버전으로 만들고 사용자 수정본을 덮어쓰지 않는다.
- 발언 내용·화자 배정·역할을 바꾸면 전사 버전을 갱신하고 이전 분석에 갱신 필요 상태를 표시한다.
- 표시 이름만 바꾸는 경우 안정적인 화자 ID를 이용해 화면과 내보내기의 이름을 갱신한다.
- 편집 API는 기준 버전을 요구한다. 다른 탭에서 먼저 수정했으면 충돌을 알리고 조용히 덮어쓰지 않는다.
- 재분석 작업은 시작 시점의 전사 버전을 고정한다. 분석 중 추가 수정이 있으면 완료 결과를 이전 전사 기준으로 표시한다.
- 기록 삭제 시 활성 작업을 중단한 뒤 음성, 중간 파일, 전사와 분석 버전을 함께 지운다. 외부 공급자의 데이터 삭제·보관 정책까지 로컬 삭제가 제어한다고 표현하지 않는다.

Markdown에는 제목, 녹음 정보, 화자, 요약, 주제별 기록, 질문·답변, 합의, 남은 질문, 할 일, 시간과 화자가 있는 전사를 포함한다. JSON은 구조화 정보와 근거를 포함하고, 로컬 절대 경로와 비밀 설정은 포함하지 않는다.

## 9. 작업 상태와 실패 처리

파일 입력 상태와 처리 작업 상태를 구분한다. 입력은 `recording/uploading/ready/invalid`, 작업은 `queued/running/succeeded/failed/cancelled/interrupted`로 관리한다. 실행 중 작업에는 현재 처리 단계와 체크포인트가 있다. 전사 성공 후 분석만 실패하면 전사는 그대로 확인할 수 있다.

- 워커 재시작 시 미완료 작업을 식별하고 마지막 완료 단계부터 다시 실행한다. 결과 반영은 트랜잭션으로 수행해 같은 결과가 중복 생성되지 않게 한다.
- API 재시도는 네트워크 오류·속도 제한·서버 오류에 한해 최대 두 번으로 제한한다. 인증 오류·지원하지 않는 입력은 반복하지 않는다. 전송 후 응답을 못 받은 경우 외부 비용이 중복될 가능성을 처리 이력에 남긴다.
- 모델 출력 형식 오류는 한 번 교정 재시도 후 대체 경로 또는 실패 상태로 처리한다.
- 잘못된 파일, 길이·크기 초과, 디스크 공간 부족은 가능한 한 추론 전에 검사한다.
- 사용자가 취소하면 워커가 해당 단계 프로세스를 종료하고 기존 완료 결과는 보존한다. 이미 전송된 외부 요청의 과금 취소는 보장하지 않는다.
- 메모리 사용을 줄이기 위해 큰 모델 단계는 순차 실행하고 다음 단계 전에 모델을 해제한다. 동시 추론 작업 수는 하나로 시작한다.

## 10. 품질과 성능 검증

현재 PC는 Apple M5 Pro·메모리 48GB다. 로컬 모델의 실제 품질과 처리 시간은 아직 측정하지 않았다. Ollama와 `gpt-oss:20b`, Node.js, uv는 확인했고, FFmpeg와 FFprobe는 PATH에서 발견되지 않았다. 음성 모델 준비와 의존성 설치는 구현 단계에 포함한다.

아래 수치는 **검토를 위한 초기 제품 목표**이며 측정 결과나 성능 보장이 아니다.

| 항목 | 초기 목표 |
| --- | --- |
| 깨끗한 한국어 1:1 전사 | 정답 전사 대비 문자 오류율(CER) 10% 이하. NFC 정규화 후 공백·문장부호를 제외하고 숫자·단어 표기는 유지 |
| 깨끗한 1:1 화자 구분 | 화자 구분 오류율(DER) 10% 이하. 경계 허용 구간 0ms, 겹친 발화 포함 |
| 처리 시간 | 모델이 준비된 이 PC에서 60분 녹음을 전사·화자 구분·분석까지 15분 안에 완료 |
| 분석 근거 | 모든 사실 항목에 유효한 근거 발언 ID가 있고, 사람의 검토에서 근거 없는 결정·담당자·기한이 없음 |
| 대화 보존 | 질문·답변 관계, 핵심 수치와 부정 표현을 사람이 확인 |
| 내보내기 | JSON 검증 통과, 화면과 Markdown·JSON의 전사 및 분석 버전 일치 |

대표 녹음에는 또렷한 교대 발화, 짧은 맞장구, 겹침, 작은 목소리, 배경 소음, 긴 침묵, 한국어·영어 용어 혼용을 포함한다. 정답이 있는 최소 30분의 평가 구간과 별도의 60분 연속 녹음으로 정확도·화자 ID 유지·처리 시간을 확인한다. 평가 자료가 준비되기 전에는 품질 검증을 완료했다고 표시하지 않는다.

같은 평가 구간에서 로컬과 API를 비교하고, 단계별 오류율·처리 시간·메모리·외부 사용량을 기록한다. 자동 모드의 로컬 기본값은 품질과 속도 목표를 모두 만족하는 조합으로 정한다. 기준을 넘지 못한 단계에는 API를 사용하고, 모든 단계를 통과하면 로컬에서 완결한다. 평가 보고서에는 실제 사용한 모델과 버전을 고정해 기록한다.

제품 동작 검증은 실제 음성의 사람 평가와 별도로 수행한다. 파일 입력부터 결과 조회·내보내기까지의 연결, 타임스탬프 이동, 전사 수정과 분석 갱신, 존재하지 않는 근거 ID 거부, 무음 처리, 워커 중단 복구, 로컬 전용 모드의 외부 요청 차단을 검증한다. 유료 API를 호출하지 않는 테스트와 실제 엔진 검증을 구분한다.

## 11. 첫 릴리스의 완료 조건과 후속 범위

첫 릴리스는 마이크 녹음·파일 입력에서 재생 가능한 화자별 전사, 원문과 연결된 구조화 기록, 수정 후 재분석, 로컬 저장·재실행, Markdown·JSON 내보내기까지 한 흐름으로 동작해야 한다. 로컬 전용 실행이 실제로 가능하고, API 설정 시 부족한 단계를 외부 처리로 완료할 수 있어야 한다. 목표를 충족하지 못한 품질 항목은 측정 결과와 함께 명시한다.

실시간 전사, 여러 사용자·공유·로그인, 녹음 간 자동 인물 식별, 다수 녹음을 대상으로 한 검색·질의, 모바일 앱, 시스템·통화 음성 직접 캡처, 음성 트랙 분리, PDF·DOCX 내보내기는 후속 범위다. 전사와 분석 버전·근거 ID를 보존해 추후 검색과 AI 연동의 기반으로 삼는다.
