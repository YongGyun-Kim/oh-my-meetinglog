# 4. Plaud의 공개 방식과 비교 원칙

이전: [대화 처리 단계](03-conversation-pipeline.md) · [읽기 안내](README.md) · 다음: [우리 프로젝트](05-project-walkthrough.md)

학습 목표는 Plaud가 공개한 수음·전처리·전사 흐름을 설명하고, 우리가 재현할 수 있는 부분과 확인하지 못한 부분을 구분하는 것이다. 공개 자료 확인일은 2026-10-19다.

## 4.1 무엇을 벤치마크하는가

Plaud는 전용 녹음 장치와 앱·웹·클라우드 처리를 결합한 제품이다. 우리는 녹음에서 전사·화자 구분·요약·검토로 이어지는 흐름을 참고한다. 기존 파일을 입력하는 기능도 비교 대상이다.

이 프로젝트는 Plaud의 비공개 코드를 분석하거나 내부 모델을 복제한 것이 아니다. 공개 자료를 읽어 원리를 이해하고, 우리 입력과 환경에 맞는 공개 모델로 별도의 시스템을 만든다.

## 4.2 Note와 Note Pro를 구분한다

공식 비교 문서는 다음 마이크 구성을 제시한다. MEMS는 작은 반도체 기반 마이크를 만드는 기술이다. VPU는 제품 사양의 표기를 그대로 적었다. 내부 처리 칩·센서의 상세 구성까지 확인했다는 의미는 아니다.

| 항목                      | Plaud Note                           | Plaud Note Pro                           |
| ------------------------- | ------------------------------------ | ---------------------------------------- |
| 공식 마이크 구성          | 2 MEMS + 1 VPU                       | 4 MEMS + 1 VPU                           |
| 녹음 모드 전환            | 수동 Dual Mode                       | Smart Dual Mode                          |
| 이 문서에서 참고하는 범위 | 전용 수음 장치와 통화·대면 녹음 구분 | 다중 마이크와 전사·재생 경로의 공개 설명 |

[Plaud 공식 Note·Note Pro 비교](https://support.plaud.ai/hc/en-us/articles/50218478191257-What-is-the-difference-between-Note-and-Note-Pro)

마이크 개수만으로 전사 품질을 순위 매길 수는 없다. 배치, 발화자 거리, 방의 울림, 입력 장치 설정, 후속 모델이 함께 영향을 준다. Note Pro의 설명을 모든 Plaud 기기에 그대로 적용하지 않는다.

통화 녹음에는 기기를 전화기에 부착하는 조건도 있다. 공식 지원 문서는 이어폰 사용 시 상대 소리를 받지 못할 수 있다고 설명한다. 우리 브라우저의 일반 마이크 녹음과 같은 수음 조건이 아니다. [공식 음질·통화 수음 안내](https://support.plaud.ai/hc/en-us/articles/52138800203545-Low-volume-or-poor-sound-quality-on-Plaud-Note)

## 4.3 공개된 기술 설명

제조사의 Transcription API 소개는 방향성 수음·빔포밍, 기기 내 신호 처리, 업로드 전 스펙트럼 차감과 적응형 필터링, 자체 화자 구분 파이프라인을 설명한다. 모델명·가중치·파라미터·전체 실행 순서까지 공개한 명세는 아니다. [Plaud 개발자 설명](https://dev.plaud.ai/transcription-api/)

여기서 쓰인 용어를 일반 원리로 풀면 다음과 같다.

- **빔포밍:** 여러 마이크의 시간·위상 차이를 이용해 특정 방향의 소리를 강조한다.
- **스펙트럼 차감:** 주파수별로 추정한 잡음 성분을 줄인다.
- **적응형 필터링:** 입력과 환경의 변화에 맞춰 필터 계수를 갱신한다.

이 일반 설명만으로 Plaud가 사용하는 수식, 필터 구조, 신경망 종류를 특정할 수는 없다. ‘AI 빔포밍’이라는 제품 표현도 그 자체로 재현 가능한 알고리즘 명세는 아니다.

## 4.4 전사용 음성과 재생용 음성이 다를 수 있다

Plaud의 기술 글은 4개 마이크와 Note Pro를 예로 들어, 재생에는 잡음을 억제한 신호를 제공하고 전사에는 발화 방향과 발음 세부 정보를 보존하는 별도 신호를 사용한다고 설명한다. 다음 그림은 그 공개 설명을 단순화한 것이다. 필터의 정확한 순서나 전체 제품 구조를 의미하지 않는다. [제조사의 기술 글](https://www.plaud.ai/blogs/news/the-trade-off-between-sounding-good-and-transcribing-accurately)

```mermaid
flowchart LR
    A[여러 마이크의 입력] --> B[수음·신호 처리]
    B --> C[재생에 맞춘 경로]
    C --> D[사람이 듣는 음성]
    B --> E[전사에 맞춘 경로]
    E --> F[ASR에 전달하는 음성]
```

이 설계에서 배울 점은 작업별 목표를 나누는 것이다. 배경 소음이 줄어 사람이 편하게 듣는 결과와, 자음·작은 응답을 보존해 모델이 정확하게 읽는 결과는 다를 수 있다.

제조사는 특정 잡음 조건의 자체 실험도 제시한다. 그 수치를 우리 한국어 회의의 예상 오류율로 사용하지 않는다. 입력·거리·엔진이 같지 않고 독립 재현도 하지 않았기 때문이다.

다른 공식 도움말은 AI Speech Enhancement가 전사와 재생에 도움을 줄 수 있다고 설명한다. 두 설명을 종합하면 잡음 제거의 효과는 조건에 따라 평가해야 한다. 공개 자료만으로 제품 버전별 적용 경로를 모두 확정할 수 없다. [음성 강화 도움말](https://support.plaud.ai/hc/en-us/articles/50609692751257-AI-Speech-Enhancement)

## 4.5 장치에서 녹음한다고 전사까지 장치에서 끝나는가

녹음 장소와 추론 장소를 구분한다. Plaud Embedded의 공개 흐름에는 장치, 모바일 앱, 사용자의 백엔드, Plaud 클라우드 서비스가 있다. 녹음 파일을 동기화하고 파일 URL을 클라우드에 전달해 전사를 받는 경로를 명시한다. [Plaud Embedded 구조](https://docs.plaud.ai/plaud-embedded/overview)

즉, 오프라인에서 녹음할 수 있다는 사실만으로 전사·요약까지 오프라인이라고 판단하면 안 된다. 위 문서는 Embedded 연동 경로의 근거이며 모든 소비자 앱 내부 호출 순서를 증명하는 자료는 아니다.

전사 이후에는 화자 라벨 수정과 전문 용어 사전 같은 개선 수단도 있다. 전문 용어의 올바른 표기를 모델에 전달하는 것은 파형의 잡음을 줄이는 작업과 다르다. [공식 전사·화자·사용자 사전 안내](https://support.plaud.ai/hc/en-us/articles/53793130069657-Transcribe-and-summarize)

## 4.6 우리 환경과의 비교

| 비교 항목 | Plaud 공개 설명                         | 우리 현재 구현                                   |
| --------- | --------------------------------------- | ------------------------------------------------ |
| 수음      | 전용 장치, 제품별 다중 마이크·통화 수음 | 브라우저 마이크 또는 기존 파일                   |
| 원시 채널 | 장치 배열을 활용한 처리 설명            | 녹음 시 모노 요청, 모델용 파생본도 모노          |
| 전처리    | 빔포밍·잡음 완화·작업별 경로 설명       | 원본 보존과 16kHz 모노 변환, 별도 강화 모델 없음 |
| 전사 실행 | Embedded 문서의 클라우드 경로           | 기본 로컬 MLX, 선택 가능한 OpenAI 경로           |
| 화자·시각 | 전사 결과의 화자 라벨 제공              | 별도 정렬·화자 모델의 시간 정보를 결합           |
| 품질 근거 | 제조사의 공개 설명·자체 실험            | 짧은 합성 음성 실행 확인, 실제 대화 품질 미검증  |

우리 구현의 근거는 [녹음 코드](../../web/src/features/recordings/useRecorder.ts), [파생본 생성](../../backend/src/meetinglog/recordings/media.py), [음성 모델 연결](../../backend/src/meetinglog/engines/local_speech.py)이다.

현재 브라우저는 echo cancellation·noise suppression·auto gain control을 끄도록 요청한다. 기기·OS·브라우저의 전체 수음 처리가 사라졌다고 단정하지 않는다. 실제 설정 확인 API인 `getSettings()` 결과를 현재 앱이 저장하는 기능도 아직 없다. [실제 트랙 설정 확인 API](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings)

## 4.7 우리에게 적용하는 판단

다음은 현재 선택 또는 후속 실험 방향이다.

1. **현재:** 수신 원본을 덮어쓰지 않고 모델용 파생본을 만든다.
2. **현재:** 큰 모델을 순차 실행하고 전사·화자·정렬 오류를 검토 표시로 남긴다.
3. **후속 실험:** 잡음 강화본과 최소 변환본을 같은 정답으로 비교한다.
4. **후속 실험:** 원시 다채널을 확보한 경우 공간 처리의 효과를 별도로 평가한다.
5. **후속 실험:** 전문 용어·수치·부정 표현을 위한 오류 자료를 축적한다.

Plaud와의 직접 비교는 실험 질문에 따라 설계한다. **전체 제품 비교**라면 같은 대화를 동시에 녹음해 수음부터 결과까지 비교한다. **전사 엔진 비교**라면 가능한 한 같은 파일을 넣어 수음 차이를 통제한다. 두 실험의 결론을 섞지 않는다.

## 4.8 확인 문제

1. Note Pro의 4마이크 설명을 기존 Note에 그대로 적용해도 되는가?
2. 제조사 자체 실험을 우리 앱의 한국어 정확도로 보고해도 되는가?
3. 잡음 제거를 켜면 음성이 듣기 좋아졌을 때 무엇을 더 확인해야 하는가?

<details>
<summary>해설</summary>

1. 안 된다. 제품 구성과 공개 범위가 다르다.
2. 안 된다. 같은 입력·조건으로 직접 측정한 값이 아니다.
3. 정답 전사와 비교해 발음·짧은 응답·수치·조건이 더 잘 보존됐는지 확인한다.
